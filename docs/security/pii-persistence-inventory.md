# PII persistence inventory and migration order

**Status:** verified source inventory, not a claim that these records are encrypted.

The Electron renderer currently owns several synchronous stores. These paths serialize JSON into browser storage; interview sessions are also written as JSON files under Electron `userData`. The new main-process `PiiVault` is an encryption primitive and IPC boundary only. Until each owner below is migrated and its legacy data is verified, existing records remain plaintext.

## Explicitly lower sensitivity / not included in the first PII migration

UI preferences such as `teleprompter_opacity`, `interview_audio_device_id`, `interview_speech_pause_tolerance`, `interview_response_mode`, and `preferred_coding_language` are not candidate content by themselves. They should remain separate from PII records unless future review identifies identifying content.

Provider API credentials have a separate Electron `safeStorage` implementation in `electron/services/credentialStore.ts`; they are not to be copied into the PII vault.

## Migration invariants

1. Hydration must be asynchronous in the renderer. Do not initialise a PII store from plaintext `localStorage` in Electron and then silently continue as if protected.
2. Read the encrypted record first. If it exists but keyring access/decryption fails, surface a locked/error state; do not fall back to stale plaintext and do not overwrite the encrypted record.
3. For a legacy plaintext record, write the encrypted record, read it back, compare the normalized payload, and only then remove the legacy key.
4. If keyring access, quota, disk write, or verification fails, preserve the plaintext source and report that persistence is not complete.
5. Writes must be serialized per record to prevent an older debounced write from overwriting a newer value.
6. Reset/delete must remove encrypted and legacy copies and report partial failure. A successful UI reset must not leave an older encrypted copy to reappear on restart.
7. Export/import remains an explicit plaintext user action. Export files are user-controlled and must not be described as encrypted.
8. Audio recordings, temporary OCR files, caches, and arbitrary attachments need a separate file/blob migration and retention decision; this inventory does not claim they are covered.

## Delivery sequence

- **Stage 1 (this PR):** main-process vault, OS-wrapped random data key, AES-256-GCM records, context binding, atomic writes, fail-closed keyring checks, and test coverage.
- **Stage 2:** migrate canonical profile and candidate knowledge vault, including all hidden/internal write paths and clear/reset behaviour.
- **Stage 3:** migrate practice and CareerOps Zustand stores with async hydration, write queues, failure UX, and rollback-safe localStorage migration.
- **Stage 4:** migrate session history and JSON files; audit audio, recordings, attachments, temporary files, and caches.
- **Stage 5:** packaged macOS Keychain, Windows DPAPI, and Linux Secret Service/KDE Wallet validation; recovery/export/import and key lifecycle tests.

**Current limitation:** Stage 1 alone does not encrypt the existing localStorage keys or session JSON files. Issue #72 must remain open until Stages 2–5 are complete and tested.
